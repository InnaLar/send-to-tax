Сервис принимает чеки (`receipts`) и отправляет их в налоговую через `SendReceiptJob`.
Появилось новое бизнес-требование — **возвраты**: покупатель вернул покупку, и по ранее
доставленному чеку нужно оформить возврат.

Оформление возврата состоит из двух частей:

1. зарегистрировать возврат у нас в БД (новая таблица + обновление чека);
2. уведомить внешний сервис **ТФК**, который ведёт учёт возвратов.

Считаем, что ТФК уже существует и у него есть API:
```
POST {tfk.base-url}/api/v1/refunds
Content-Type: application/json

{
  "refundId":  123,        // id возврата в нашей системе
  "receiptId": 45,         // id чека
  "sum":       "1500.00"   // сумма чека
}
```

Ответ `200 OK` — возврат принят. Сервис внешний: может отвечать `5xx`, может таймаутить.
`tfk.base-url` вынести в `application.yaml` (по аналогии с `TaxClient` / `TaxClientConfig`).

## Что нужно сделать

1. **Таблица `refunds`** — миграция `V4__create_refunds.sql`:
    - `id` (PK), `receipt_id` (ссылка на `receipts`), `created_at`, `status`;
    - по одному чеку возможен только **один** возврат.

2. **REST-эндпоинт** `POST /api/v1/receipts/{id}/refund` (контроллеров в проекте ещё нет —
   это первый). Тело запроса не нужно, id чека берём из пути.

3. **Валидации:**
    - чек существует — иначе `404`;
    - чек доставлен в налоговую (`processed = true`, `status = SUCCESS`) — иначе `409`;
    - возврат по этому чеку ещё не оформлялся — иначе `409`.

4. **Логика оформления возврата:**
    - создать запись в `refunds`;
    - перевести чек в статус `REFUNDED` (расширить `ReceiptDeliveredStatus`);
    - отправить уведомление в ТФК (отдельный клиент по образцу `TaxClient`).

5. **Требование консистентности:** если клиент получил успешный ответ — возврат оформлен
   в БД **и** ТФК о нём знает. Если оформить возврат не удалось — в БД не должно остаться
   никаких следов (ни записи в `refunds`, ни смены статуса чека), а клиент получает ошибку.

## Критерии приёмки

- Миграция накатывается, приложение стартует.
- Интеграционные тесты (Testcontainers, как в существующих; ТФК мокать —
  `MockRestServiceServer` или WireMock):

| Сценарий | Ожидание |
|----------|----------|
| happy path | `200`, запись в `refunds`, чек в `REFUNDED`, в ТФК ушёл правильный JSON |
| чека нет | `404`, БД не изменилась |
| чек не доставлен / возврат уже есть | `409`, БД не изменилась |
| ТФК ответил `500` | клиент получил ошибку, в БД нет следов возврата |

## Подсказки

- Клиент для ТФК делайте по образцу `TaxClient` + `TaxClientConfig` — отдельный
  `RestClient` со своим base-url.
- Подумайте, на каком слое жить логике оформления возврата: контроллер должен остаться
  тонким.
- «Один возврат на чек» — это не только проверка в коде. Что произойдёт, если два запроса
  на возврат одного чека прилетят одновременно?
